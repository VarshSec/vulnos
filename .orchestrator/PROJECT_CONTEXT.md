## 1. Product Mission & Philosophy

VulnOS is an **evidence-driven, AI-assisted web and API vulnerability discovery platform** designed exclusively for authorized offensive security assessments, continuous attack surface management (ASM), and automated penetration testing.

### Core Architectural Principles:
1. **Authorized Scope Only:** Every single network operation, port connection, HTTP exchange, or DNS resolution MUST be checked and authorized against active written authorization and scope rules. No network traffic is ever sent to unauthorized destinations.
2. **Evidence-Driven Findings:** Vulnerability discoveries are never asserted by generative AI hallucinations. An issue is recorded if and only if verifiable evidence (HTTP requests/responses, tool output, screenshots, execution exit codes) is cryptographically captured and stored.
3. **Defense-in-Depth Scope Enforcement:** Dual-gate isolation:
   - Control-Plane Gate: Orchestrator validates target destination before creating or dispatching any task.
   - Data-Plane Gate: Containerized workers route all egress through an isolated allowlisting egress proxy that rejects unauthorized traffic.
4. **Untrusted Worker Sandboxing:** External scanner tools (Subfinder, Nmap, httpx, etc.) and AI agent harnesses run inside hardened, unprivileged Docker containers (non-root, read-only root filesystems, all Linux capabilities dropped, no Docker socket access). Workers do not decide their own scope.
5. **Deterministic State Transitions:** Both reconnaissance jobs (`Scan`) and individual tasks (`ToolExecution`) are governed by deterministic, transactional state machines with hierarchical row-level locking.

## 3. Disambiguation: Product Orchestrator vs. AI Engineering Orchestrator

To eliminate architectural confusion, two distinct concepts use the term "Orchestrator":

| Dimension | VulnOS Product Orchestrator | VulnOS AI Engineering Orchestrator |
|---|---|---|
| **Location** | `backend/app/recon/` and `engine/orchestrator/` | `.orchestrator/` and `.github/` |
| **Domain** | Vulnerability scanning runtime | Software development lifecycle (SDLC) |
| **Entities** | `Scan`, `ToolExecution`, `AgentRun`, Celery tasks | GitHub Issues, PRs, Git branches, CI checks |
| **Actors** | System, Celery workers, timeout controller | AI Engineering Manager, Antigravity Agent, Reviewers |
| **Mission** | Execute authorized scans against target assets | Build, test, review, and ship VulnOS platform code |

## 4. Key Architectural Invariants

Every agent working on this codebase MUST uphold these non-negotiable rules:
1. **Target is a Seed:** A registered target in `targets` is a discovery seed, not permission to scan. Network operations require an active `AuthorizationRecord` and matching `ScopeRule`.
2. **Hierarchical Locking:** Whenever modifying a `ToolExecution`, the parent `Scan` row lock MUST be acquired FIRST, and the `ToolExecution` row lock SECOND.
3. **Server-Controlled Timestamps:** Timestamps (`started_at`, `finished_at`) must be generated by server UTC clocks. Never trust client or worker timestamps.
4. **Append-Only Audit Logging:** Lifecycle transitions, lease claims, and result submissions must persist an `AuditLog` entry in the same transaction.
5. **No Secret Leakage:** Secrets, bearer tokens, passwords, and API key peppers must never appear in log messages, audit metadata, error responses, or test traces.
6. **Fail-Closed Design:** In the event of scope ambiguity, missing authorization, or worker attempt mismatch, the system MUST fail closed and deny execution.
